## 逐项详情

### 1. SSE ✅

- 主轮采集 0 字节的疑点定性：`Start-Process curl` 后台采集方式问题（非服务端）；
  前台 curl 两轮均正常收帧。
- 收口轮（非提权，RunKey 轮询判定不依赖 ETW）：`retry: 3000` 帧 + 
  `event: verdict` 帧 ×1，帧体 `{"action":"audit","pid":0,"rule_id":"persistence",…}`
  与 `/api/verdicts` 落库行一致。断连重连（retry 语义）与鉴权矩阵已有单测覆盖。
- 偏差表「SSE 未实现→轮询」正式归位。

### 2. 场景 A：探测路径对短命句柄无效（⚠️ 维持已知缺口）

- 实测（三轮）：`resolved=10 unknown=44 probe_tried=2 probe_hit=0`；`.git` 事件始终
  未进入 `[file]` 管线；cmd `type` 的读路径 Read 事件（op=67）在修复前后均等不到
  Name 事件。
- 根因（比 M1 结论更进一步）：ETW 缓冲投递延迟（数十 ms 量级）大于 `cmd /c type`
  毫秒级句柄存活期——探测发起时句柄已关，句柄表查不到该 FileObject。
  probe_tried 仅 2 次/轮是 150ms 限流的预期行为（burst 下主动降频）。
- 一轮曾有 probe_hit=1/2（certutil 场景，长命句柄可命中）——探测机制本身工作，
  但对场景 A 的短命句柄无效。
- **去向**：备选方案改为 Security 审计通道（Event ID 4663，需 SACL，M1 报告
  已列），或对 `.git` 目录设全局 SACL 的部署侧方案；探测代码保留（长命句柄
  场景仍有效），未知率监控指标已上线（file_probe_tried/hit）。

### 3. 场景 C：判定链打通，字节来源修正 M1 结论（⚠️→部分归位）

- **判定链端到端实证**：树内 curl POST 8MB（阈值 5MB）→ `[处置] 断连接
  192.168.1.34:54668 -> 13.223.216.61:80` + `[处置] 封禁 …（600s）` +
  net-threshold Block 判定落库（两轮 ×2）。**M1「阈值不可观测」的结论修正：
  本机 ETW send 事件足以支撑阈值判定**（本轮 99 条 send 事件累计 5.0MB；
  M1 观测的「8MB body 仅 1 条 176B 头部事件」不具普适性——与传输路径/时机相关）。
- **estats 路径本机不可用**：三轮定位 `SetPerTcpConnectionEStats` 本身返回
  rc=50（ERROR_NOT_SUPPORTED），即本机（Win 26100）TCP estats Data 集合整体
  不可用（非缓冲/参数问题——评审修复的 24B ROD 与 NOT_FOUND 区分逻辑保留）。
  **去向**：estats 轮询对本机降级为 best-effort（连接表保留、Set 失败不重试），
  字节计数以 ETW send 为主路径；Linux/macOS 不受影响（无 estats 依赖）。

### 4. WFP ✅

- 场景 C 触发封禁后：`netsh wfp show sublayers/filters` XML 均含
  HarnessGuard（filter id=317768 实证）；服务日志 `[wfp] 过滤器 id=… 已装
  （13.223.216.61 出站阻断，动态会话）`。
- 强杀服务后：**过滤器消失**（动态会话随进程回收，netsh 复核）；
  **子层残留**（持久会话装配，评审修复的设计行为，无副作用）。
- 偏差表「netsh→WFP」正式归位（netsh 保留为 BFE 不可用时的降级路径）。

### 5. TaskScheduler ✅（修复一项实机 bug 后）

- **实机暴露 bug（已修，8783db5）**：provider GUID 原写
  `de7b246a-cffa-…`（不存在的 provider），正确为
  `de7b24ea-73c8-4a09-985d-5bdadcfa9017`（注册表 `WINEVT\Publishers` 核对）。
  静态评审无法发现此类错误——实机复验的价值实证。
- 修复后三轮：`schtasks /create`（树内发起）→ 通道启用 +3s → 106 事件流入 →
  `[持久化] 计划任务注册：\HG-M4-R3（user=…，pid=0，未归因…）` →
  persistence audit 判定 ×3 落库。
- **pid 归因**：三级链走到第三级（pid=0 未归因）——第二级 cmdline 特征扫描
  存在时机竞态（106 事件到达时发起 cmd 已退出）。判定与告警不受影响；
  归因优化（扫描窗口提前缓存候选）入待修清单。
- 通道状态：复验期间临时启用，结束后已恢复 disabled（原状态）。
